## Measured on the public #51062 branch

M3 Ultra, 512 GB, branch `inkling2-metal-fp4@0edf7e4`, model
`thinkingmachines/Inkling-2-Mini`, config `base-4bit`, `hc_bench.py`, 6 x 128 tokens:

- **38.86 tok/s**, samples 38.82-38.89, coherent text.
- `HC_GROUP=1` + `use_kernels=True`: **38.13 tok/s** and **garbage output** (token salad).
  Rejected. The `use_kernels=True` path falls back on a `causal_conv1d` hub kernel that
  is wrong for this build; the warning is `causal_conv1d_fn` is falling back.
- Without `use_kernels`, `MetalFp4Experts` is active and output is coherent.

So the public PR is a memory/functionality win, not the 55-59 tok/s performance branch.
**UPDATE: the branch was pushed after this check.** `huggingface/transformers` now has
`inkling2-metal-perf@fb89fd0` (kernel pin `e00b93b7` in the branch; set
`HC_KERNEL_REV=8d84318f15ece7e2334a89573dcbeac1952b37e4` for the best pin).

Reproduced on M3 Ultra, `base-4bit`, `HC_GROUP=1`, 6 x 128 tokens:

- **79.14 tok/s** (78.93 / 79.18 / 79.06 / 79.13 / 79.27 / 79.14), coherent text.
- `HC_GROUP` monkeypatch reports `grouped 0` because the branch's quantizer already
  fuses the sibling projections at load.
- Public #51062 branch without the perf branch: 38.86 tok/s.

Memory after load: `current_allocated 10.5 GiB`, `driver_allocated 18.0 GiB` after
`empty_cache`, process footprint 18 GB. **Peak footprint during the on-the-fly dense
quantization was 37 GB**, so a 32 GB Mac will swap/OOM at load. A pre-quantized dense
Inkling checkpoint is needed for a true 32 GB run, the same fix as the Qwen3.8 final
checkpoint.

## AOTI command-block runner

Implemented and validated separately: `mps-concurrency/aoti_runner/`.

- Pure-Metal AOTI graph, 2 independent kernels: 0.317 -> 0.286 ms (1.11x), exact.
- 8 independent 65K kernels: 0.294 -> 0.340 ms, exact; runner overhead wins.
- Mixed `sin -> cumsum -> cos`: custom Metal cumsum removes the PyTorch-stream flush,
  but is slower (0.546 vs 0.381 ms) and not bit-identical (4.6e-5 / 1.5e-4).
- Replacing PyTorch ops with Metal kernels only helps if the replacement beats the
  PyTorch op in-context; cumsum does not.

## Why Inkling had on-the-fly quantization, and the 0-call checkpoint

The source `thinkingmachines/Inkling-2-Mini` checkpoint is **not** a final Metal
checkpoint for the always-on layers. Its config says `modelopt/NVFP4`, but that covers the
expert banks. The dense/attention/MLP linears are bf16. `hc_bench` then passes
`"*": MetalConfig(4, 64)`, a **runtime plan**: `MetalQuantize` packs every bf16
`nn.Linear` during load. That is the on-the-fly quantization and the 37 GB peak. The
experts are native and pre-quantized, so `MetalFp4Experts` does not dequantize them.

Qwen3.8's final checkpoint avoids this because the 725 always-on linears were packed
offline and the config plan points at them (`quantized 0 nn.Linear`, `on-the-fly
quantization calls: 0`). Inkling had no equivalent checkpoint.

Built one (`inkling2/final_checkpoint/make_final_inkling_checkpoint.py`):

1. load with the runtime Metal plan, but disable `fuse_sibling_linears` while saving so
   the checkpoint keeps the loader's original keys (`q_proj.linear.weight`, ...);
2. save the packed `MetalLinear` weights/scales/qbiases and the native `MetalFp4Experts`
   banks;
3. write a config plan with the per-expert NVFP4/FP8 entries, `lm_head` Metal, `*` Metal,
   and `model.visual.*` / `*_message_gate` None;
4. add the U32 init skip (`0001-inkling-skip-u32-init.diff`); otherwise the loader runs
   float initializers on packed uint32 weights.

Result:

| load | on-the-fly calls | driver after empty_cache | footprint | peak |
|---|---:|---:|---:|---:|
| source + runtime plan | 201 quantized linears | 24.9 GiB | 18 GiB | **37 GB** |
| final checkpoint | **0** | **17.8 GiB** | **18 GB** | **18 GB** |

The final checkpoint generates the same text as the source 4-bit path on the lighthouse
prompt in this test (both loop in the reasoning preamble at 128 greedy tokens: 69.8 vs
64.3 tok/s in the direct test). The loop is model/prompt/4-bit-dense behavior, not a
checkpoint-corruption difference; the original `hc_bench` 79.1 tok/s run used the same
runtime plan and is the reference for speed.

Qwen3.8 already has the equivalent final checkpoint:
`ArthurZ/Qwen3.8-Flash-Next-metal-experts-4bit-final`.
